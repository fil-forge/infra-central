# Shared staging runs protected, single-AZ infrastructure

The shared staging environment runs in `us-east-2` in the sandbox AWS account. It uses the
delegated `staging.fil-forge.com` and `staging.filonecontent.com` zones and deploys on every merge
to `main`, after the same pull-request plans that protect dev.

## The database is small, protected and single-AZ

Staging uses a single-AZ `db.t4g.small` RDS PostgreSQL instance with 20 GiB of gp3 storage. Storage
may autoscale to the module's 100 GiB ceiling. The initial allocation is enough for staging and has
the same gp3 baseline performance as any allocation below 400 GiB, while the small instance gives
the shared application and OpenBao databases 2 GiB of memory and roughly 225 connections.

OpenBao may use 16 Postgres connections. Automated RDS backups are retained for seven days and
Performance Insights stays enabled.

The VPC still spans two availability zones because the ALB and RDS subnet group require them. One
NAT gateway serves both zones. The database has no standby, Global Accelerator stays disabled and
Container Insights stays disabled.

`protect_stateful_resources` is enabled. This turns on deletion protection for RDS, the ALB and
both DynamoDB tables, enables DynamoDB point-in-time recovery, retains a final RDS snapshot and
uses the 30-day KMS deletion window. The S3 buckets refuse a destroy while they contain objects
because `force_destroy` is disabled.

## Application tasks keep the existing defaults

Sprue, Hilt and OpenBao each receive 0.5 vCPU and 1 GiB of memory. Swarf, Delegator, Signing
Service and PLC each receive 0.25 vCPU and 0.5 GiB. Every service runs one task. No task requests
additional ephemeral storage beyond Fargate's default allocation.

Staging initially pins the image digests already running in dev. Later service and provision Lambda
versions move to staging in deliberate promotion pull requests after they are healthy in dev. The
Lambda promotion copies the digest already stored in the ECR repository both stages share. The
automated image-bump workflow continues to update dev only.

Sprue may provision storage without a funded payment plan, matching the previous shared staging
deployment. Services log at `info`.

## Identities use the staging namespaces

Central configures these service identities:

- Sprue: `did:web:upload.staging.fil-forge.com`
- Indexing Service: `did:web:indexer.staging.fil-forge.com`
- Signing Service: `did:web:signer.staging.fil-forge.com`
- Delegator: `did:web:delegator.staging.fil-forge.com`
- Hilt: `did:web:auth.staging.fil-forge.com`
- Swarf: `did:web:revoke.staging.fil-forge.com`

The Indexer identity is minted and used to issue Delegator's proof, but staging does not deploy an
Indexing Service or create a public Indexer route. The Signing Service keeps the existing behavior
where its configured `did:web` has no published DID document.

OpenBao remains public at `ssm.staging.fil-forge.com`, which appliances use to unseal. PLC remains
public at `plc.staging.fil-forge.com`, which appliance Ingots use for DID resolution. Neither is an
additional service identity in the list above.

## The eu-central-3 appliance remains externally operated

Central creates an OpenBao transit key for the `eu-central-3` appliance and derives its Ingot
identity as `did:web:s3.eu-central-3.staging.filonecontent.com`.

Piri and Ingot are not deployed or sized by this repository. Piri's public URL is
`https://piri-0.staging.fil-forge.com`; its `did:key` and proof are generated by the appliance and
supplied when it is onboarded. The appliance's machine, blob volume and DNS records belong to its
own infrastructure.

## CI owns deployment after bootstrap

The staging platform and apps use `staging/platform.tfstate` and `staging/apps.tfstate`. The
non-prod CI roles receive access to that state prefix before the first staging plan runs.

Pull requests report `plan-staging-platform` and `plan-staging-apps`. A merge applies the platform,
then the apps, waits for every ECS service to reach steady state and tests the public endpoints.
Failed staging deploys print staging logs and feed the shared deployment alert.
